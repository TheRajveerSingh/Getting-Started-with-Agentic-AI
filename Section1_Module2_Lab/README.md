8. The "07.1_Embedding Models, Vector Stores, and Retrievers" file is the basics to the introduction of how RAG Architectures are built. Here I learnt about Vector Embeddings. Basically how does an AI know which chunks are the important and relevant ones from where information should be extracted from. Every chunk's embeddings are stored in ChromaDB, and those chunks whose embeddings match most similarly to the embeddings of our 'question', those relevant chunks are only sent to the AI. I also learnt about what happened if chunks had ambiguous words(their vector becomes a blend of both meanings), and how to handle chunk size carefully, as smaller ones can loose context, while larger ones can loose real meaning. Some examples of Vector Stores ae: ChromaDB, FAISS, Pinecone, Milvus. We also learn about two types of Retrievers: Vector store-backed retrievers, and parent document retrievers.

10. The "7.3_Retrieval QA Learning Exercise" file describes how can we build a simple Retrieval system using LangChain. As always, we load a Document into a Document Loader (either a PDF os a web-based Doc), which helps to store this Document in a Document Object. Then, we define how much the chunk size and overlapping should be using the 'text_splitter'. According to this 'text_splitter', we create the chunks of the doc (from the document object) and save it in a Container. Now, we define an embedding model (the model used to give embeddings to each chunk). We define it using which model we may want to use to do this job, what should be its parameters, etc. The Next step was to convert the chunks to its vector embeddings and store it in a 'vector store'. Lastly, we could create a retriever, to retrieve information according to what we need.
This file also taught me about the "Garbage In, Garbage Out" principle of RAG. The exercise was to build a simple retrieval system from a LangChain webpage, but it went wrong in two ways. First, the code crashed because the embedding model I was using was no longer supported. Then, after fixing the model, every query returned the exact same, useless snippets. Then we diagnosed the main issue: the TRUNCATE_INPUT_TOKENS parameter was set to 3, which meant the embedding model was only reading the first three words of every chunk and query, destroying all their meaning. After fixing that, the pipeline worked, but the results were still chaotic. This was the "Garbage In, Garbage Out" problem. The webpage I was scraping was a high-level landing page full of navigation menus and UI buttons, not deep paragraphs of text. The retriever was doing its job perfectly, but it was forced to pull the "closest matching" vectors it could find, which turned out to be junk. The final breakthrough was when I fed the vector store clean, intentional mock documents. Every single query then matched its perfect answer. This proved that the RAG pipeline itself was flawless; the problem was the data source. The key takeaway was that in production RAG,we must use data cleansing techniques to feed the pipeline clean data, or we'll get confused answers from the LLM.
